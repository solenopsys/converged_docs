# Доступ к объектам

## Два уровня, а не один

Доступ к методам и доступ к объектам отвечают на разные вопросы, и ни один из
них не заменяет другой.

**Доступ к методу** — может ли этот субъект вообще вызвать `rp/community/listTopics`? Он хранится в дереве разрешений, выдаётся через `rp-access` и проверяется защитным механизмом nrpc до запуска обработчика. Без него любой может вызвать `deleteTopic`.

**Доступ к объекту** — какие темы возвращает `listTopics`? Об этом данный документ. Без него субъект, которому разрешён вызов `listTopics`, получает все темы в хранилище.

Доступ к объектам повторно использует транспорт доступа к методам, а не добавляет вторую систему: тег — это обычное разрешение в пространстве имён `tg`, передаваемое тем же JWT и выдаваемое теми же вызовами.

## Механизм

Две вещи, обе локальные для сервиса, которому принадлежат данные.

Одна таблица на хранилище, обслуживающая все типы объектов в нём:

```sql
CREATE TABLE access_tags (
  objectId TEXT NOT NULL,
  tag      TEXT NOT NULL,
  PRIMARY KEY (tag, objectId)
);
CREATE INDEX access_tags_object ON access_tags (objectId);
```

И теги, по которым сопоставляется субъект. Столбца типа объекта нет: соединение с таблицей-владельцем выполняет эту фильтрацию, поскольку идентификатор, принадлежащий другому типу, там не найден.

## Теги

**Теги групп** — `team-support`, `moderator`. Хранятся для каждого пользователя в KV-хранилище `access` сервиса `rp-access`, внутри существующего дерева разрешений как `tg/<tag>/*(mode)`, и передаются в JWT. Выдаются с помощью `addTagToUser`.

**Персональный тег** — `u-<userId>`. Никогда не хранится и не выдаётся: он выводится из субъекта токена, который уже присутствует в каждом проверенном токене. Объект, открытый одному человеку, помечается тегом этого человека, поэтому индивидуальное разрешение занимает одну строку и ничего в токене.

**Хорошо известные теги** — `public` (кто угодно, включая анонимных вызывающих) и `authenticated` (любой проверенный субъект). Видимость определяется тем, каким из этих тегов помечен объект, а не столбцом, благодаря чему каждая выборка остаётся поиском по тегу.

Таким образом, владение, индивидуальное предоставление доступа, доступ групп и публичная видимость — это один механизм с четырьмя видами тегов, а не четыре механизма.

## Выборка

Выборка должна начинаться с таблицы тегов и соединяться с объектами. `visibleFrom` в `back-core/access` делает именно это:

```ts
import { listVisible, visibleFrom } from "back-core";

const page = await listVisible<Topic>(this.store.db, "topics", { limit: 50 });

const custom = await visibleFrom(this.store.db, "topics")
  .selectAll("obj")
  .where("obj.status", "=", "open")
  .orderBy("obj.id")
  .limit(50)
  .execute();
```

Направление — не вопрос стиля. При записи в плоском виде — `access_tags JOIN topics ... WHERE tag IN (...) ORDER BY topics.id` — SQLite предпочитает сканировать таблицу объектов в порядке первичного ключа, чтобы удовлетворить сортировку. В таблице размером в миллион строк, из которых видимы десять, это заняло **363 мс** для страницы из пятидесяти строк. Через подзапрос, который строит `visibleFrom`, та же страница заняла **0.28 мс**. Оба варианта возвращают идентичные результаты, поэтому форма запроса проверяется тестом плана выполнения, а не результата.

Никогда не фильтруйте после запроса, за пределами базы данных, и никогда не храните теги в столбце-списке, проверяемом для каждой строки: оба подхода читают всю таблицу.

`listVisible` возвращает `totalCount`, рассчитанный с тем же сужением, что и страница. Подсчёт без него раскрывает, сколько объектов скрывается.

## Выдача разрешений

```ts
const access = new AccessTags(this.store);

await access.tagNew(id, { owner: actorId, visibility: "private" });
await access.grantToUser(id, otherUserId);   // effective immediately
await access.revokeFromUser(id, otherUserId);
await access.dropObject(id);                 // on delete; a leftover row would
                                             // later match a reused id
await access.requireRead(id);                // throws AccessDeniedError
```

Членство в группе проходит через `rp-access`, поскольку оно хранится в токене:

```ts
await access.addTagToUser(userId, "team-support");
await access.removeTagFromUser(userId, "team-support");
await access.getTagsOfUser(userId);
```

## Требования

**Идентификаторы должны быть уникальны во всех таблицах, охватываемых тегами.** Общая последовательность, UUID или префикс типа — в зависимости от того, что уже используется хранилищем. Сущности, не охватываемые тегами, не затрагиваются; это не повсеместный переход платформы на UUID.

**Идентификаторы должны генерироваться сервером.** При отсутствии столбца типа объекта идентификатор, который может выбрать вызывающий, становится объектом, к которому вызывающий может получить доступ. Идентификаторы, задаваемые клиентом, сегодня существуют в `rp-sales`, `rp-classifier` и `rp-chats`; их необходимо устранить до внедрения тегов в этих репозиториях.

**Монотонные идентификаторы — преимущество, а не требование.** Общая последовательность или UUIDv7 дают порядок создания непосредственно из индекса тегов. UUIDv4 этого не делает, и это единственное последствие — вместо этого передавайте явный `orderBy`.

**Порядок байтов должен соответствовать смыслу.** Числовая последовательность, хранящаяся в текстовом столбце, требует дополнения нулями, иначе `"10"` будет отсортировано перед `"9"`.

**В идентификаторах и тегах не должно быть `:` или `;`.** В `back-core` они являются `KEY_SEPARATOR` и `RANGE_END_SUFFIX`; разделитель внутри ключа делает его неоднозначным в KV-хранилищах. `addTagToUser` отклоняет такие теги.

**`NRPC_ACCESS_MODE` должен иметь значение `required`.** При отключённой защите пользователь контекста берётся из конверта, который записывает вызывающий, — тогда персональный тег выводился бы из идентификатора, заданного клиентом. В `confs/dev` и `confs/prod` установлено значение `required`; значение по умолчанию в коде — `off` для локальных запусков и тестов.

## Хранилища, не использующие SQL

KV: та же форма ключей в том же хранилище — `tag:<tag>:<objectId>` для прямого направления и `obj:<objectId>:<tag>` для обратного. Чтение списка — это сканирование префикса для каждого тега с последующим объединением и удалением дубликатов. Для честной пагинации в `kvList` нужен курсор, а сейчас он возвращает весь диапазон; до тех пор списки KV ограничены объёмом, помещающимся в памяти.

Файлы и JSON (`JsonStore` расширяет `FileStore`): собственного индекса тегов нет. Имя файла — это идентификатор объекта, а доступ к нему определяется доступом к записи, которая на него ссылается; эта запись находится в SQL- или KV-хранилище того же сервиса.

Граф: тег — это узел, разрешение — ребро, обход начинается с тега.

## Допустимые ограничения

**Удаление тега группы ждёт перевыпуска токена** — `DEFAULT_TTL_SECONDS` равен 90 дням. Индивидуальные разрешения и отзываются немедленно, поскольку таблица читается при каждом запросе. Доступ, который должен измениться сразу, использует персональный тег, а не группу.

**Точный `totalCount`** требует соединения; при нескольких пересекающихся тегах подсчёт выполняется по уникальным идентификаторам, что становится дороже по мере роста видимого набора.

**Сортировка по любому полю, кроме идентификатора,** дёшева, пока тегу соответствует небольшое число объектов. Если один тег когда-либо охватит сотни тысяч объектов, этот порядок придётся денормализовать в таблицу тегов или отказаться от него.
